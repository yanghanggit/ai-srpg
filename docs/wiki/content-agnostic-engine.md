# 内容无关引擎（Content-Agnostic Engine）

蓝图是引擎的输入，不是引擎的一部分。引擎执行机制，故事由蓝图提供；判断一段文本或代码归哪一侧，只问一句：换个故事，它还成立吗。

## 三条分界线

- **结构词汇与题材词汇**：引擎认识角色、舞台、世界、道具这类结构角色——它们描述一个东西在世界里承担什么；不认识帝国、教团、灵能、星神。舞台按树存储：根是自带网格的大地图，直接子舞台是占据一格的地点，地点内部成图；角色只属于某一个舞台。题材名词出现在引擎源码里即越界。
- **机制与值**：引擎提供机制（实体、组件、system 管线、事件、快照、会话历史），蓝图只能为机制填值，不能造机制。题材需要引擎没有的能力时，那是引擎的一次演进，不能靠往蓝图堆字段绕过。这条界定了「换故事不换引擎」的真实含义——换的是内容与既有机制的取值。
- **骨架与内容**：引擎只负责段落顺序（游戏设定、实体设定、全局规则、扮演约定），骨架里的话全部来自蓝图。

## 引擎内允许的文本

段落顺序本身是设计决策：agent 先读到所处的世界，最后读到必须遵守的规则。扮演语法是跨题材恒定的约定，例如实体全名仅供系统路由、不构成世界内可感知信息。事实性叙述只陈述状态——谁在哪个舞台、此刻在场者是谁。

事实性叙述是这条原则的代价项：事件载荷是文本，引擎必然要为 agent 生成句子。约束落在尺度上，只陈述状态，不带情绪、修辞与题材语气。

## 内容的位置

内容分两层。故事定义风格与正典——战役设定、全局规则、世界职责，对本故事下所有剧本生效；剧本才装配蓝图，提供自己的世界、舞台与角色，因此同一套故事可以并行多个起点，用于开发与测试的不同阶段。两层都属于输入侧，引擎对它们无感。

数据流单向：蓝图进入构建期，之后以快照为真相，事件只往会话历史与 job 事件走，没有一步回写蓝图。所以同一份蓝图可以反复开局，每一局的差异留在自己的快照序列里。

重建蓝图产物用 `uv run python -m scripts.build_blueprint --source dark_fantasy/mercenary_camp --game Game1`：只写蓝图与留痕，不碰数据库，因此换故事换剧本都不必清库，已有快照的局仍按快照恢复。

蓝图在出厂时导出各实体的提示词，设定是否跑偏在开局前就能看见。

实体名是纯字符串：只用于索引与显示，引擎不按分隔符解析它。名字里写出层级是给人读的，不是给代码算的。

蓝图里的一个实体只承载三样东西：名字、进游戏后的第一条记忆、组件数据。类别不在枚举里，而是由标记组件表达；装配期会要求实体确实带对了标记组件——漏写当场失败，不会留下一个谁都不认识的实体。

## 已知边界

- **题材级分类不进枚举**：枚举是编译期契约，写进题材分类就要改引擎；题材需要的分类走组件数据。
- **组件表是引擎资产**：蓝图能为实体填组件值，组件类本身属于引擎。因此换故事的前提是新故事能落在既有机制上，否则是一次引擎演进。
- **实体语义由蓝图承载**：角色、舞台、世界各自承担什么写在全局规则里，引擎只拼段落骨架、不写实体定义。这段文字因此是内容对结构契约的唯一表述，改动时以引擎的实际行为为准。
- **提示词骨架是中文**：内容也须用中文书写，否则骨架与内容语言割裂。

## 防线

输入侧的闸门拦的是「这一份内容写错了」。引擎侧能机械校验的只有依赖方向：引擎不得引用种子数据，源码里也不得出现蓝图声明的实体名。题材词汇无法穷举，其余靠评审——标准仍是那句「换个故事，它还成立吗」。
